## LFM3-Omni vision 路径：CPU 侧基础（Session 8）

- 从 HF 镜像取得 LFM3-Omni-2B 的完整视觉参考实现（15 个小文件，310 KB，放在
  `.lfm3-real/omni-ref/`），并在 findings.md 锁定视觉塔的精确规范。
- 纠正上一轮调研的两处错误：塔内 norm 是 **RMSNorm**（只有投影器入口是 LayerNorm）；
  `mm.0` 是 4096→4096（2×2 spatial merge）。另确认 HF RMSNorm 权重是 `w`（无 `1+w`），
  GGUF `ne` 按 C-order 读出即 HF `[out,in]`，无需转置。
- 新增 `tools/convert_lfm3_mmproj.py`（numpy，仿 tools/convert_qwen4_exp.py）：把用户的
  270 MB mmproj GGUF 转成 BF16 safetensors + `vision_config.json` + `conversion.json`。
  139 → 140 张量，381,922,984 B，产物在 `.lfm3-real/vision-omni/`。输出刻意不叫
  `config.json`，避免覆盖主模型文件夹配置。
- 关键结论：两个 `v.patch_embd` 卷积核是 HF `Linear(1536→1024)` 的两个 temporal 半，
  必须按 `[c,t,ph,pw]` **交错**拼接（与 HF 权重首行逐位一致）；相加/简单拼接都错
  （相关性仅 ~0.75）。两核彼此相关 0.968，光靠相关性判断不出来。
- 验证：自检 24/24、回读 140/140；独立纯 struct 重解析 GGUF 抽样 973 个值全部匹配；
  HF BF16 range 读取交叉验证（patchifier / embedding_norm 逐位一致，Q4_0 `mm.0`
  corr 0.9982）。ruff + py_compile 通过。
- 陷阱：safetensors 的 `data_offsets` 必须加 `data0 = 8 + header_len`（本例 84872）。
- 未做（需 GPU 窗口）：`src/vision/lfm3_vit.cpp`、新 Metal 内核、引擎 image-token 接线、
  HF 特征对比。没有声称任何 GPU 验证。中文贪心自环问题仍未诊断。
